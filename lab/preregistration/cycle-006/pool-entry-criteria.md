## 1. What this document is

Two things, and nothing else:

1. **Normative prose** (§§2–14) — the human-readable statement of every criterion, what evidence it demands, and why each value is what it is.
2. **Exactly one canonical machine block** (§15) — the only part any tool reads. It is emitted as canonical JSON (sorted keys, no insignificant whitespace) so that the document digest cannot drift on formatting, and so that the block the tooling parses is byte-identical to the block a reviewer reads.

Where the prose and the machine block could be read differently, **the machine block governs the tooling and the prose governs the reviewer**; a divergence between them is a specification defect to be corrected by re-issue, never resolved by preferring one at run time.

### 1.1 The two mechanical disciplines that make these criteria outcome-blind

**Every numeric value is a derived-value envelope.** No bare number appears anywhere in the machine block except the document `revision`. Every other number is written as `{ "value": …, "derivation_ref": … }`, and every `derivation_ref` resolves into the CI-line derivation worksheet — a measured constant with four-leg provenance, a frozen experimental parameter, a row of the mechanically derived cadence/history envelope, or a **declared Gate-P operator decision** whose own `evidence_ref` points back into that worksheet. The survey tooling refuses a block containing an unprovenanced number, and a separate check resolves every reference (C6-FR-P5, AC-C8).

**Every operator-reserved value was an explicit sentinel until EC settled it, never a guess.** While this document was `PENDING_GATE_P`, each value belonging to EC — the pool bounds, `k_max` and the FR-D2 budgets, the rank function, the credential posture, the source universe, and the sweep procedure — stood as `{ "operator_decision_required": true, "decision_id": … }`. At `GATE_P_FIXED` **zero** sentinels may remain, and the tooling refuses a Gate-P-fixed document with an undecided slot. The implementing agent therefore could not have quietly fixed an operator-reserved value, and Gate P could not have been declared over a half-decided document. §14 records what EC decided, alongside the recommendation and the lawful alternatives that were put to it.

## 2. Admission is a conjunction, never a judgment

A provider-product is **admitted** if and only if:

1. **every** candidate-scope criterion verdict recorded in the survey record is `pass` (§§3–12), **and**
2. the candidate is **selection-relevant** on its authored inputs (§13).

There is no weighting, no discretionary step, and no override. The tooling reads recorded verdicts and computes; a missing verdict, a verdict without a citation, or an authored value without a `standard_ref` is a **refusal**, never a default. Both possible statuses are recorded for every consulted provider-product: `SURVEYED_ADMITTED` or `SURVEYED_REJECTED`, the latter naming the specific failed criterion (C6-FR-N3).

**Candidate rejection, and failure to constitute a lawful pool at all, are valid outcomes.** If a complete sweep of the declared universe admits fewer selection-relevant members than the Gate-P minimum, the cycle ends at the typed pre-freeze disposition **`no-lawfully-constitutable-pool`**, carrying the complete survey record as its primary evidence. That is an honest, informative negative. It is never repaired by relaxing a criterion mid-survey (which would be a full Gate-P re-issue and a complete re-survey, §16) and never repaired by padding the pool (which §13 forecloses mechanically).

## 3. §(a) Documented lawful aggregate-count surface — `C-A-count-surface`

**Standard.** The candidate provider publishes an aggregate observation-count surface for the product, reachable without value-level contact. The criterion is satisfied only when **all three** of the following are present and citable:

- the **provider-published field name** that carries the count;
- the **document citation** (document and section) where that field is published;
- the **documented semantics** of that field — what it counts.

Absent any one of the three, the candidate is refused. "Documented" is a **citation standard, not a judgment call**: a reviewer can check each of the three against the cited document without forming an opinion.

**Basis.** C6-FR-P4(a). This standard exists because Cycle-005's deciding evidential question was exactly this one — whether a candidate's count surface was published, named, and semantically documented (the rank-1 `count_nu` finding; the rank-4 inventory-surface finding). That prior evidence informs **this standard** and privileges **no provider** (§1.2).

**Count-surface class.** Two classes are declared, and the class is recorded with the verdict:

- `published-count-field` — the provider publishes an explicit observation-count field;
- `published-inventory-derivable` — the count is derivable from a published inventory or catalogue surface without value contact.

The class ordering (`published-count-field` before `published-inventory-derivable`) is the criteria-declared evidential-directness order. It is fixed here, before any candidate exists, and is the first key of the Gate-P-accepted rank function (§14, decision P-3).

## 4. §(b) No-value-contact route class — `C-B-no-value-contact-route`

**Standard.** A documented metadata or documentation route class exists that yields every required aggregate field **without contacting a value-bearing endpoint or response shape**. The route class is established by citing provider documentation — never by issuing a trial request, which would itself be contact.

**Basis.** C6-FR-P4(b). Aggregate-only acquisition is the inherited FR-B1–B4 discipline and standing invariant I-8. A candidate whose only count surface is value-bearing cannot be measured lawfully by this apparatus, so it is not admissible regardless of its other merits.

## 5. §(c) Mechanically derived cadence / history / runtime envelope — `C-C-cadence-history-band`

**Standard.** The candidate's documented cadence class is one of the criteria-declared classes whose derived runnability band is **non-empty**, and the provider-documented available history satisfies that class's band lower bound.

**The band is derived, not chosen.** For each cadence class `c`:

- **lower bound** = `max(gate3_min_years, gate3_min_n / obs_per_day(c) / 365.25)` — the frozen gate-3 floors (≥ 3 years **and** ≥ 10⁴ observations). The existence-margin sub-condition clears automatically at n ≥ 10⁴, so it imposes no additional floor.
- **upper bound** = `T_max(c) = N_ci / (obs_per_day(c) × max_slice_fraction)` — the point beyond which the observation count implied by the class exceeds what the frozen classifier can process on the supported CI node line.

`N_ci` (the classifier input ceiling) and `max_slice_fraction` are **measured on the CI node line** across the binding matrix `{ubuntu-latest, windows-latest} × node {20, 24}` and aggregated conservatively — MIN across legs for every ceiling-type constant, MAX for every cost-type constant (SDD DR-3.3). Local values from a developer machine are recorded in the worksheet only under `advisory_local_values`, labelled advisory-only, and are never aggregated.

**The derived table** (every value carries a `derivation_ref` into the worksheet):

| class | obs interval | obs/day | band lower (y) | band upper (y) | margin (days) | admissible |
|---|---:|---:|---:|---:|---:|---|
| `c60` | 60 s | 1440 | 3.000 | 0.299 | −986.6 | **no** |
| `c300` | 300 s | 288 | 3.000 | 1.494 | −550.2 | **no** |
| `c900` | 900 s | 96 | 3.000 | 4.481 | +541.0 | yes |
| `c3600` | 3600 s | 24 | 3.000 | 17.924 | +5451.1 | yes |
| `c21600` | 21600 s | 4 | 6.845 | 107.546 | +36781.3 | yes |
| `c86400` | 86400 s | 1 | 27.379 | 430.185 | +147125.2 | yes |

`c60` and `c300` are **mechanically inadmissible**: their gate-3 history floor exceeds `T_max(c)`, so no lawful experimental span exists for them. That is a derived fact, not a policy choice.

**EC declined to restrict the admissible set further (§14, P-9).** `c900`, `c3600`, `c21600`, and `c86400` are operator-affirmed admissible; `c60` and `c300` remain mechanically inadmissible. The admissible set is therefore exactly the set of classes whose derived band is non-empty — no more, no less.

**The cadence sweep predates every candidate.** The six classes swept are structural measurement inputs fixed in the LU-1 derivation harness before any criterion was authored and before any candidate existed. Nothing in the table was selected to fit anything.

## 6. §(d) Reserve runnability — `C-D-reserve-runnability`

**Standard.** The candidate's cadence class band is non-empty **with a recorded positive margin** (`band_margin_days > 0`).

**Why it is a separate criterion.** The frozen selection rule seals a primary **and a reserve**, and either may be the member a later cycle actually runs. Requiring runnability at **admission** means every admitted member — hence every possible sealed member — is experimentally runnable **by construction** (C6-FR-P4(d), C6-FR-P8). It is recorded as its own criterion, mechanically equal to the cadence table's `admissible` flag, so that the reserve-runnability obligation is separately auditable rather than buried inside §5.

This criterion is one half of a restrict-only pair. Its post-selection partner, the runnability validity condition pre-registered in the successor preregistration, can only convert a computed seal into a typed terminal disposition. Neither can re-rank, substitute, or admit.

## 9. §(g) Provider-product identity and independence — `C-G-identity-independence`

**Identity.** The candidate identity is the **exact `(provider, product)` string pair**, joined as `<provider>/<product>` — the granularity the frozen reconciliation matches on and the granularity the burned-list join takes as its input. Survey identity matching is **exact-string**: no normalization, no case folding, no fuzzy join.

The frozen burned-list predicate applies its own normalization to that pair before joining (case folding and non-alphanumeric collapse). That is **strictly more conservative** than exact-string matching — it catches strictly more burned matches, never fewer — so exact-string survey identity can never smuggle a burned candidate past the frozen gate.

**Duplicate handling.** A repeated `(provider, product)` identity anywhere in the survey is a **refusal** — never a merge, never last-wins. A filename slug may be derived for file naming only; it is never an identity.

**Independence — two limbs, both binding.** No two admitted members may share a controlling publishing authority, **and** no two may republish the same underlying measurement programme. The second limb binds **independently of the first and regardless of controlling-authority labels**: two products under two differently-labelled authorities that republish one measurement programme are dependent, and the rule applies. Where a dependent pair is found, the **later-encountered member in sweep order** is refused and recorded as `SURVEYED_REJECTED(C-G-identity-independence)` — a mechanical rule, never a judgment about which of the two is better.

Because the sweep order is the declared portal order (§14.3), same-authority precedence is deterministic and was fixed before any candidate existed: `noaa-coops-web-services` precedes `noaa-ndbc-web-data-guide`, and `usgs-earthquake-catalog-api` precedes `usgs-water-data-apis`. A later same-authority portal is refused for dependence **only when an earlier product from that authority has already been admitted** — the rule bites on admitted members, not on portals.

This is what keeps the pool from being one provider in five costumes, which would manufacture the appearance of mechanical competition over what is in substance a foregone selection.

For each, a mechanical or citation-based admission standard is precommitted here — **never a per-candidate judgment formed after the candidate is known**. Every authored value recorded for a candidate must carry a `standard_ref` into this block **and** a citation satisfying that standard; a value missing either is a refusal.

| ref | value | standard (summary) |
|---|---|---|
| **K-1** | `authority_published` | The publishing organisation is the **authority of record** for the measurement programme, evidenced by the provider's own documentation identifying it as publisher of record. A mirror, aggregator, or redistributor is false. |
| **K-2** | `public` | Provider documentation states the product is available to the general public without membership, institutional affiliation, or an application process. |
| **K-3** | `machine_readable` | The provider documents a structured, parseable distribution format (a named format, schema, or record layout). A human-readable page alone is false. |

| **K-5** | `exogeneity_judgment` | A recorded written judgment that **must** cite (i) the documented physical or administrative **generating process** of the series and (ii) the documented **absence of any feedback path** from FORGE-side or market-side use of the series into that generating process. A judgment citing only "no obvious feedback path", without the generating process, is refused. |
| **K-6** | `exogenous` | True only when the K-5 judgment is recorded and **both** required citations are present and support non-reflexivity. Any unresolved reflexivity concern makes it false. |
| **K-7** | `mechanical_outcome_declared` | A realized-future-value outcome function can be declared from **provider-documented semantics alone**, with no human labeling, adjudication, or discretionary revision step anywhere in the outcome path. ## 13. §(i) Pool bounds, selection relevance, and no padded pools — `C-I-pool-bounds`

**Selection relevance (C6-FR-N8).** A provider-product that, **on its authored inputs alone**, would fail an authored hard gate **in its most favorable lawful completion** of its not-yet-measured fields is `SURVEYED_REJECTED(authored-gate:<gate>)` and is **never admitted**. A candidate surviving this test is *selection-relevant*: it could become primary or reserve under some lawful completion of its census-measured fields.

**The probe is the frozen rule, reused — not reimplemented.** The tooling builds

> most-favorable census stand-in **⊕** the candidate's authored gate values **⊕** the exact `(provider, product)` identity

and runs it through the frozen `applySelectionRule`. That is the **same overlay order** the frozen invariance layer uses for its Tier-2 most-favorable-completion exclusion, and it enters the frozen rule at the same entry point (`eligibility.js` is never imported — the G9 discipline). Because both sides call the same frozen function with the same composition rule, admission-time and invariance-time **cannot** diverge; a conformance test asserts their agreement on shared fixtures. The most-favorable stand-in is asserted byte-equal to the frozen invariance stand-in fixture.

**Bounds, as fixed at Gate P (P-2).** The pool holds **at least 3** selection-relevant members and **at most 6**. Members that are not selection-relevant **never** count toward the minimum. Falling below the minimum after a complete sweep is the typed ending `no-lawfully-constitutable-pool` (§2), never a relaxation and never a padding.

The maximum of 6 is not an arbitrary ceiling: the declared eight-portal universe (§14.3) maps to **six controlling authorities**, so under the first independence limb (§9) six is the largest pool the universe can mechanically yield. The bound is therefore binding rather than decorative, and the second independence limb may reduce the reachable maximum further.

**FR-D2 bounds, as fixed at Gate P (P-2b).**

| bound | value | role |
|---|---:|---|
| `k_max` | **6** | maximum simultaneously-unresolved candidates the evaluator will accept; equal to `max_pool`, so a lawful full-pool unresolved state stays evaluable |
| `probe_budget` | **20** | ceiling on `2 full + 3k single` frozen-rule probes; `2 + 3×6 = 20` is an exact fit, not a breach |
| `n_ceiling` | **24 120 603 015** | ceiling on any observation count entering an existence-bound computation |
| `corroboration_budget` | **1000 ms** | projected-cost ceiling under which the definitional enumeration ALSO runs, as corroboration |
| `wall_clock_target_seconds` | **60** | the operator-fixed policy target the `n_ceiling` was sized against — a policy value, **not** a frozen empirical constant |

They are **restrict-only**: breaching one produces a typed fail-closed escalation (`FR_D2_KMAX_EXCEEDED`, `FR_D2_BUDGET_EXCEEDED`), never a hang, never a partial verdict, and never a silent seal. The worksheet records the measured cost slope and fixes no wall-clock target of its own; the 60-second figure is EC's policy choice, recorded here as such.

## 14. Deterministic ranking, and the operator decisions Gate P settled

### 14.1 The rank function's form was fixed here; its content is EC's

**Form (fixed, not negotiable).** The rank is an ordered tuple of sort keys drawn from a **closed registry of criterion-derived attributes**, terminated by a **lexicographic ascending `(provider, product)` tie-break**. Three properties follow mechanically:

- **No candidate-authored key can enter the sort.** An attribute outside the registry is a refusal. Two of the three registered attributes are pure functions of this document plus the candidate's documented cadence class; the candidate supplies no number that reaches the comparator.
- **The order is total by construction.** `(provider, product)` pairs are unique (§9), so the terminal key always decides. The tooling **appends** it rather than reading it from the declared tuple, so no declared tuple can leave a tie for a human to break.
- **No per-candidate authored rank exists anywhere.** Ranks are assigned `1..N` contiguously by sorting — the unique-integer-≥-1 floor the frozen assembly layer enforces and the frozen selection rule refuses without. **EC accepted the function; never a ranking.**

**The registry.**

| attribute | type | derived from |
|---|---|---|
| `count_surface_class` | enum (`published-count-field` → `published-inventory-derivable`) | §3 verdict |
| `cadence_obs_interval_seconds` | number | §5 cadence table |
| `history_band_margin_days` | number | §5 cadence table |

**The accepted tuple (P-3).** `count_surface_class` ascending, then `cadence_obs_interval_seconds` descending, then `history_band_margin_days` descending — terminated by the tooling-appended lexicographic `(provider, product)` tie-break, which is never declared in the tuple.

### 14.4 The declared sweep procedure — `cycle-006-survey-procedure-2`

Seventeen steps, digest-fixed in the machine block (`survey_procedure.steps`). The procedure does not exist only in prose. Revision 2 revises steps 3, 4, 5, 8, 11, and 12 to bind product-family discovery to the fixed enumeration index and the fixed product-family definition (§14.5). The step count, the traversal rule, the stopping rule, and every other step are unchanged.

1. Traverse the eight portal entries strictly in the declared order.
2. For each portal, begin only from its declared root and provider-published documentation or specification pages linked from that root.
3. Discover the product families of a portal from that portal's fixed `enumeration_index_url` alone, applying the fixed product-family definition. The fixed enumeration index is the sole product-family discovery authority; it may not be substituted, replaced, reinterpreted, or supplemented by another page, and no choice between the declared root and any other index is available to the survey.
4. 5. Build the complete product-family list for each portal from its fixed enumeration index before applying any admission criterion. Canonicalize duplicate labels and inspect the resulting product families in lexicographic product-name order.
6. Use only uncredentialed, provider-published documentation and specification pages.
7. Do not invoke an API, query builder, data-download route, live station page, current-conditions page, dashboard, visualization, sample-data link, or other value-bearing surface.
8. Record every product family discovered from the portal's fixed enumeration index, whether admitted, rejected, indeterminate, or blocked by unavailable documentation.
9. For every rejected product, record the first mechanically failed criterion and its provider-published citation. Do not stop surveying the remaining product families merely because the Gate-P minimum has already been met.

13. Do not follow documentation links outside the declared controlling authority official domains, except links to an official federal specification explicitly incorporated by the provider.
14. If a documentation page unexpectedly exposes live or measured values, stop reading that page, create the required typed survey-contamination event, and do not silently use the exposed values.
15. Do not add, replace, or remove a portal or product-family source during the survey.
16. Any universe change requires: a revised criteria digest; a new Gate-P acceptance; invalidation of the prior survey; a complete survey restart from portal 1.
17. Survey completion means: all eight portals reached a complete or explicitly operator-adjudicated state; every discovered product family is recorded; every admission or rejection is reproducible from the fixed criteria and citations alone; no unrecorded provider-product consultation occurred.

### 14.5 The fixed product-family definition

Revision 1 defined a surveyable product as "a separately named top-level data service or product family listed by the declared root **or** its official product/service index," with no rule for choosing a limb when the two exposed different granularities, and with no official index declared anywhere. That disjunction admitted two mutually exclusive, outcome-determining enumerations of the same portal. **That is a specification defect, and revision 2 repairs it.**

**A product family is** a provider-named leaf API or machine-readable data service in the fixed official index that:

- has its own stable provider documentation page or stable provider-authored section; **and**
- has no child entry in that same official hierarchy that is itself named as an API or service.

**The following are not product families:**

- categories or grouping headings;
- endpoints or methods;
- parameters or variables;
- datasets or series;
- stations, sites, or locations;
- files or formats;
- examples;
- dashboards, query builders, report generators, widgets, visualizations, or helper tools.

**Apply this taxonomy rule before any admission criterion.** Family discovery for a portal is complete before the first criterion is evaluated against any family of that portal.

**Do not use cadence, history, admissibility, expected yield, or pool sufficiency to choose the hierarchy level.** The level is decided by the provider's own naming and the leaf test alone. Choosing a granularity after observing which granularity yields admissions is outcome-**aware** selection — precisely the act §1.1 and §15 exist to foreclose.

The rule has **one** mechanical interpretation because each of its inputs is fixed before the sweep: one index per portal (§14.3, no choice of source), the provider's own naming (not the surveyor's), and a leaf test that is decided by the presence or absence of a child entry named as an API or service in that same hierarchy. A category with documented child services is therefore never a family; a child endpoint or method under a service is never a family.

If the fixed index cannot produce a unique family set under this rule, the portal routes to `pre-freeze-halt` (step 12). No substitute index or interpretation may be chosen during the survey.
